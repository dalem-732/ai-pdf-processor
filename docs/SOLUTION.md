## 1. Задача

На входе PDF, скачанный с сайта госзакупок (ЕИС, zakupki.gov.ru): извещение,
документация об аукционе, проект контракта. На выходе структурированная
выжимка из четырёх обязательных разделов:

| Раздел | Поле ответа | Что попадает |
|------|-------------|--------------|
| Сумма контракта | `contract_price` | НМЦК числом, валюта, признак НДС, дословная цитата |
| Сроки выполнения | `deadlines` | Начало, окончание, длительность, этапы, цитаты-обоснования |
| Требования к исполнителю | `requirements` | Пункты с категорией, признаком обязательности и страницами |
| Штрафы | `penalties` | Нарушение, вид санкции, формула расчёта, фиксированная сумма |

Дополнительно возвращаются предмет закупки, заказчик, номер закупки, размеры
обеспечения заявки и контракта, предупреждения о качестве извлечения и оценка
полноты выжимки.

Выжимка нужна для решения "участвовать или нет", поэтому к ней два требования,
которые важнее скорости и красоты: **прослеживаемость** (каждый факт
привязан к странице исходника) и **честность** (сервис сообщает о критичных
пропусках и сомнительных суммах; часть полей дополняется правилами без
отдельного предупреждения).

## 2. Почему задача сложнее, чем "отправить PDF в LLM"

Наивное решение "весь текст → один запрос → готово" разбивается о четыре
свойства реальных файлов с ЕИС.

**Объём.** Документация на 80–150 страниц - норма. Это 200–400 тысяч символов,
что не влезает ни в контекст локальной модели (8k токенов - типичный
работоспособный максимум для 7B на CPU), ни в разумный бюджет облачной LLM.
Значимых фактов при этом - несколько абзацев.

**Вёрстка.** PDF не хранит абзацы: перенос строки в нём - элемент оформления.
Требование "Опыт исполнения не менее двух контрактов за\nпоследние три года"
физически состоит из двух строк, а колонтитул "Страница 14 из 87" врезается
между ними. Любой анализ по предложениям без предварительной склейки работает
по обрывкам фраз.

**Таблицы.** Штрафы почти всегда оформлены таблицей "нарушение → мера → размер",
а график работ - таблицей этапов. Плоское извлечение текста склеивает такую
таблицу построчно, стыкуя строку одного столбца со строкой другого, и на выходе
санкция оказывается привязана к чужому нарушению - ошибка хуже, чем отсутствие
данных.

**Цена ошибки в цифре.** Галлюцинация в сумме контракта не выглядит как ошибка:
это правдоподобное число в правильном формате. Пользователь не может отличить
её от правды, не открыв исходный файл, а именно чтобы этого не делать, он и
пришёл в сервис.

Отсюда четыре ответа, вокруг которых построено решение: нарезка с отбором
релевантных частей, аккуратный разбор PDF с таблицами и склейкой переносов,
map-reduce с детерминированной стадией слияния, сверка сумм контракта и
обеспечений с исходным текстом.

## 3. Архитектура

```
                  ┌─────────────────────────────────────────────┐
   PDF ─────────▶ │ app/main.py - FastAPI                        │
   (multipart)    │ лимит размера, тип файла, request_id, ошибки │
                  └───────────────────────┬─────────────────────┘
                                          ▼
                  ┌─────────────────────────────────────────────┐
                  │ app/core/pipeline.py - оркестрация           │
                  └───┬──────────┬──────────┬──────────┬────────┘
                      ▼          ▼          ▼          ▼
              ┌────────────┐ ┌────────┐ ┌────────┐ ┌────────────┐
              │ pdf/       │ │ core/  │ │ llm/   │ │ core/      │
              │ extract    │ │chunking│ │провай- │ │merge +     │
              │ текст,     │ │отбор   │ │деры    │ │validation  │
              │ таблицы    │ │частей  │ │(4 шт.) │ │сверка      │
              └────────────┘ └────────┘ └────────┘ └────────────┘
                                             │            ▲
                                             │            │
                                             ▼            │
                                      ┌──────────────────────────┐
                                      │ core/heuristics - правила │
                                      │ (проверка, fallback,      │
                                      │  скоринг релевантности)   │
                                      └──────────────────────────┘
```

Модули и их ответственность:

| Модуль | Ответственность |
|--------|-----------------|
| `app/main.py` | HTTP: приём файла, лимиты, коды ошибок, `request_id`, страница загрузки |
| `app/config.py` | Настройки из окружения, выбор провайдера, лимиты |
| `app/schemas.py` | Контракт ответа, он же схема для LLM, он же валидатор |
| `app/pdf/extract.py` | PDF → постраничный текст с таблицами, чистка колонтитулов |
| `app/core/chunking.py` | Нарезка на фрагменты, скоринг и отбор |
| `app/core/prompts.py` | Системный промпт и шаблон запроса |
| `app/llm/*` | Четыре провайдера за одним интерфейсом |
| `app/core/json_utils.py` | Восстановление JSON из грязного ответа модели |
| `app/core/heuristics.py` | Извлечение фактов правилами |
| `app/core/merge.py` | Детерминированное слияние частей, оценка полноты |
| `app/core/validation.py` | Сверка сумм с текстом, дополнение пропусков |
| `app/core/pipeline.py` | Оркестрация всех шагов |

## 4. Алгоритм по шагам

### Шаг 1. Приём файла

Файл читается порциями по 1 МБ с обрывом при превышении лимита
(`TENDER_MAX_UPLOAD_MB`, по умолчанию 25 МБ), иначе загрузка
полугигабайтного "документа" роняет процесс до всякой валидации. Тип
проверяется мягко: достаточно, чтобы совпало имя файла **или** `Content-Type`,
потому что браузеры и curl присылают то `application/pdf`, то
`application/octet-stream`. Окончательное решение принимает сигнатура `%PDF-`
в парсере, поэтому переименованный `.pdf` проверку не обманывает.

Готовность LLM-провайдера проверяется **до** чтения файла: нет смысла
выкачивать 20 МБ, чтобы затем ответить "не задан ключ".

### Шаг 2. Извлечение текста

Основной экстрактор - `pdfplumber`, резервный - `pypdf`; берётся результат,
давший больше символов. Fallback включается, если основной дал меньше 200
символов или упал с исключением (документация с ЕИС нередко собрана
конвертером, который ломает часть парсеров).

Таблицы извлекаются **отдельно** от плоского текста и рендерятся строками
`ячейка | ячейка | ячейка` под маркером `[ТАБЛИЦА]`. Это ключевое решение всего
разбора: только так штраф остаётся связанным со своим нарушением.

Далее нормализация: склейка слов, разорванных переносом, сведение пробелов,
удаление колонтитулов. Колонтитулы ищутся двумя независимыми способами:

- частотный - строка из шапки/подвала, повторяющаяся минимум на 60 % страниц
  (работает от четырёх страниц; порог защищает короткие документы, где
  повтор строки ещё не означает шум);
- шаблонный - явная нумерация (`Страница 7 из 88`, `стр. 7`) удаляется
  независимо от объёма документа, а одинокое число строкой - только в шапке и
  подвале, потому что в середине это может быть номер пункта или ячейка.

Страницы размечаются маркерами `[[стр. N]]`: по ним модель заполняет
`source_pages`, а правила восстанавливают страницу по смещению в тексте.

Если текстового слоя нет вовсе, запрос завершается кодом 422 с рекомендацией
прогнать файл через OCR. Молчаливая пустая выжимка здесь опаснее отказа:
пользователь решит, что в документе нет ни цены, ни штрафов.

### Шаг 3. Нарезка на фрагменты

Текст режется по границам страниц и абзацев на части по `TENDER_CHUNK_CHARS`
(12 000 символов ~ 3–4 тысячи токенов) с перекрытием
`TENDER_CHUNK_OVERLAP_CHARS` (800 символов). При нарезке предпочитаются границы
страниц и абзацев: разрыв посреди пункта "5.2. За неисполнение ... подрядчик
уплачивает штраф в размере" оставляет модели нарушение без санкции; перекрытие
страхует те разрывы, которых избежать не удалось. Страница, не влезающая в окно
целиком (обычно склеенная таблица), делится по абзацам, в крайнем случае по символам.

### Шаг 4. Отбор фрагментов

Каждый фрагмент получает оценку релевантности по словарю закупочной
терминологии: "НМЦК" и "требования к участнику" весят по 5, "цена контракта" и
"ответственность сторон" - 3–4, наличие суммы или даты добавляет ещё немного.
В модель уходят `TENDER_MAX_CHUNKS` (по умолчанию 12) лучших фрагментов, но
первый фрагмент включается всегда: на титульном листе заказчик, предмет и номер
извещения, а по ключевым словам о штрафах он проиграл бы скорингу.

Если отобраны не все фрагменты, в ответ добавляется предупреждение с указанием,
какую настройку поднять для полного разбора. Пользователь должен знать, что
видит выжимку по части документа.

### Шаг 5. Map - извлечение фактов моделью

Каждый фрагмент уходит в LLM отдельным запросом (система + пользовательский
промпт, требование строгого JSON). Запросы идут параллельно с ограничением в
три одновременных - компромисс: при большем числе облако чаще отвечает 429, а
локальная Ollama на одной GPU обрабатывает запросы по очереди.

Ответ проходит через восстановление JSON (снятие markdown-ограждения, вырезание
сбалансированного JSON-фрагмента с учётом кавычек, починка литералов `None/True/False`,
удаление висячих запятых, дозакрытие структуры, обрезанной лимитом токенов) и
валидацию Pydantic-схемой. Невалидный ответ на одном фрагменте не отменяет
остальные, он становится предупреждением.

### Шаг 6. Reduce - детерминированное слияние

Слияние выполняется кодом, а не вторым вызовом модели. Причины практические:

- модель на слиянии теряет пункты - из двенадцати штрафов остаётся
  "основное", причём выбор меняется от запроса к запросу;
- появляется второй источник галлюцинаций уже над сгенерированными данными,
  где исходного текста для проверки нет;
- это лишний платный вызов и лишняя точка отказа на каждый документ.

Правила слияния:

- **скаляры** - первое непустое значение (фрагменты идут в порядке документа,
  а титульный лист и раздел о цене всегда ближе к началу);
- **суммы** - первая с числом, при равенстве предпочитается запись с
  дословной цитатой: именно цитата позволяет потом сверить сумму с текстом;
- **списки** - объединение с дедупликацией, где дубликатом считается и
  вложенность формулировок (перекрытие фрагментов даёт один пункт то целиком,
  то усечённым; точное сравнение строк такие дубли пропускает), а из двух
  версий остаётся более информативная, страницы объединяются;
- **штрафы** - перед дедупликацией сортируются по информативности (наличие
  формулы и суммы), чтобы осталась запись из таблицы штрафов, а не её
  пересказ из вводного абзаца.

После слияния выполняется **очистка выжимки** (`refine_summary`):

- **этапы** - остаются только этапы выполнения работ; административные сроки
  (возврат обеспечения, открытие счёта и т.п.) переносятся в
  `deadlines.raw_mentions`, дубли "первый этап" / "Первый этап" сливаются;
- **штрафы** - остаются денежные меры (пеня, штраф, неустойка с формулой или
  суммой); исключаются РНП, одностороннее расторжение и санкции заказчика;
- **требования** - квалификация и допуск (лицензии, СРО, обеспечение) идут
  первыми; рутинные обязанности при выполнении работ ограничены по числу.

### Шаг 7. Сверка с исходным текстом

По полному тексту документа независимо от модели прогоняются регулярные
правила, и их результат используется как эталон для проверки:

1. суммы контракта и обеспечений из ответа модели ищутся в тексте; сравнение идёт по строке со
   склеенными разрядами, поэтому "12 480 500" находится независимо от того,
   обычными или неразрывными пробелами оно разделено в PDF;
2. если сумма в тексте не найдена, в `warnings` уходит предупреждение о
   возможной галлюцинации;
3. если модель и правила расходятся больше чем на рубль (копейки - это
   округление при разборе суммы прописью) - предупреждение с обоими
   значениями;
4. если модель сумму контракта не вернула, подставляется найденная правилами,
   с предупреждением; обеспечения подставляются без отметки;
5. пустые разделы сроков, требований и штрафов восстанавливаются правилами;
   для требований и штрафов - с предупреждением;
6. заказчик, предмет и отдельные поля сроков могут быть дополнены правилами
   без предупреждения; признак НДС и цитата суммы дополняются из правил, если
   модель их не заполнила.

### Шаг 8. Оценка полноты

`confidence` - доля заполненных ключевых разделов с весами: цена 0.3, сроки 0.25,
требования 0.25, штрафы 0.2. Если в модель отправлена лишь часть фрагментов
документа, оценка снижается пропорционально охвату. Критичные предупреждения
сверки (сумма не найдена в тексте, расхождение с правилами) дополнительно
уменьшают метрику.

Это не "уверенность модели", а показатель, насколько выжимку можно использовать
без обязательной ручной проверки всего PDF.

## 5. Контракт данных

Схемы Pydantic (`app/schemas.py`) работают в трёх ролях одновременно: контракт
HTTP-ответа (попадает в OpenAPI), описание требуемого JSON для промпта и
валидатор ответа модели. Одно определение вместо трёх рассинхронизированных.

Решения в схеме, которые сделаны сознательно:

- **`Money` хранит и число, и дословную цитату.** Число нужно для расчётов,
  цитата для проверки и для человека: "12 480 500,00 ... рублей, включая НДС
  20 %" несёт больше смысла, чем `12480500.0`.
- **Валидатор суммы разбирает строки.** Модель возвращает то `12480500`, то
  `"12 480 500,00"`, то `"12,480,500.00"`; десятичным считается последний
  разделитель.
- **Требования типизированы категориями** (`license`, `qualification`,
  `experience`, `staff`, `equipment`, `financial`, `documents`, `other`), а
  неизвестная категория от модели сводится к `other`, а не роняет весь ответ.
- **Штраф разложен на нарушение, санкцию, формулу и сумму.** В закупках это
  разные сущности: "пеня 1/300 ключевой ставки за день" и "штраф 5 000 руб. за
  факт" нельзя схлопнуть в одну строку без потери смысла.
- **`warnings` и `confidence` - часть контракта, а не отладочный вывод.**
  Ответ сообщает о критичных пропусках и сомнительных суммах; `confidence`
  отражает полноту четырёх ключевых разделов.

## 6. Промпт и почему он такой

Системный промпт (`app/core/prompts.py`) фиксирует роль "аналитик тендерной
документации по 44-ФЗ" и девять жёстких правил. Каждое закрывает конкретный сбой,
наблюдаемый без него:

| Правило | Что происходит без него |
|---------|-------------------------|
| Только информация из фрагмента | Модель подставляет типовые для закупок значения: обеспечение "5 % НМЦК", пеню "1/300 ставки" - даже когда в тексте другие |
| Пустое поле `null`/`[]`, не пропуск | Ключи исчезают, и валидация превращается в угадывание, чего не хватает |
| Суммы числом плюс дословная цитата | Нечем сверить ответ с текстом, галлюцинация не отличается от факта |
| Страницы из маркеров `[[стр. N]]` | Факт нельзя проверить, не перечитав документ целиком |
| Не обобщать несколько пунктов в один | Три разных штрафа сливаются в "предусмотрены штрафы за нарушения" |
| Требования - только квалификация и допуск | В список попадают десятки обязанностей подрядчика при выполнении работ |
| Штрафы - только денежные меры | РНП и расторжение смешиваются с пенями и фиксированными штрафами |
| Этапы - только работы, прочие сроки в `raw_mentions` | 21 "этап" из административных сроков и дублей "первый/Первый этап" |
| Только JSON, без markdown | Ответ приходится чинить постобработкой (она есть, но это не повод) |

Схема требуемого JSON передаётся в промпте с описанием каждого поля на русском:
для локальных 7B-моделей это заметно надёжнее, чем ссылка на структуру без
пояснений.

## 7. Защита от галлюцинаций

Четыре независимых слоя, ни один из которых не полагается на добросовестность
модели:

1. **Ограничение контекста.** Модель видит только фрагменты документа и
   инструкцию не выходить за них.
2. **Структурная валидация.** Ответ обязан пройти Pydantic-схему; всё
   лишнее отбрасывается, неизвестные категории приводятся к `other`.
3. **Сверка сумм с текстом.** Суммы контракта и обеспечений, которых нет в
   исходнике или которые расходятся с правилами, помечаются предупреждением.
4. **Прослеживаемость.** `source_pages` и дословные цитаты позволяют проверить
   любой пункт, открыв одну страницу, а не весь файл.

## 8. Обработка отказов

| Ситуация | Поведение | Код |
|----------|-----------|-----|
| Не PDF по имени и типу | Отказ до чтения файла | 415 |
| Файл больше лимита | Обрыв на чтении, без разбора | 413 |
| Битый или зашифрованный PDF | `unreadable_pdf` | 422 |
| Скан без текстового слоя | `no_text_layer` с советом про OCR | 422 |
| Нет ключа провайдера | `provider_not_configured` до чтения файла | 503 |
| Отказ на части фрагментов | Выжимка + предупреждение | 200 |
| Невалидный JSON на части фрагментов | Выжимка + предупреждение | 200 |
| Отказ на всех фрагментах | `provider_unavailable` | 502 |
| Таймаут, 429, 5xx | Повтор с экспоненциальной задержкой | - |
| 401, 404, неверная модель | Без повторов, сразу ошибка | 502/503 |

Главный принцип: **частичный результат лучше отказа**. Для документа на сто
страниц потерять один фрагмент и получить выжимку полезнее, чем потерять всё
из-за одного таймаута. Обратный принцип действует там, где частичный результат
вводит в заблуждение: скан без текста даёт отказ, а не пустую выжимку.

Повторы делаются только по восстановимым ошибкам: повторять 401 или "нет такой
модели" бессмысленно, запрос не изменится, а пользователь ждёт лишние секунды
на каждом фрагменте.

## 9. Выбор LLM-провайдера

Четыре бэкенда за одним интерфейсом (`app/llm/`), переключение - одна переменная
окружения:

| Провайдер | Когда выбирать | Особенности реализации |
|-----------|----------------|------------------------|
| `ollama` | Документация не должна покидать контур; нет бюджета | `format=json` для грамматически ограниченной генерации, `num_ctx=8192` (контекст по умолчанию 2048 обрезал бы половину фрагмента) |
| `openai` | Нужно максимальное качество на сложной вёрстке | `response_format=json_object`; настраиваемый base URL, поэтому совместим с Azure, vLLM, LM Studio, OpenRouter |
| `anthropic` | Длинные документы, аккуратность с юридическими формулировками | Системный промпт отдельным полем; на старых моделях JSON стабилизируется prefill `{`, на Sonnet 4.6+ / Opus 4.7+ - только промпт и `parse_json_object` (без temperature и prefill) |
| `stub` | Демонстрация без ключей, тесты, деградация вместо отказа | Не обращается к сети: выжимка строится правилами |

Официальные SDK не используются: каждому провайдеру нужен ровно один POST, а
`httpx` уже в зависимостях. Взамен единая логика таймаутов, ретраев и разбора
ошибок для всех бэкендов вместо трёх разных наборов исключений.

Провайдера можно переопределить на отдельный запрос полем формы `provider` -
удобно сравнить облачную модель с локальной на одном и том же документе.

## 10. Производительность и стоимость

Замеры офлайн-режима (`stub`) на демонстрационном документе: 2 страницы, 4 358
символов - 120 мс полного цикла, из них разбор PDF около 90 мс.

Оценка для реальных документов:

| Документ | Фрагментов | `stub` | `ollama` (7B, CPU) | `gpt-4o-mini` |
|----------|-----------|--------|--------------------|---------------|
| 5 страниц | 1 | ~0,2 с | 20–40 с | 3–6 с |
| 40 страниц | 4–5 | ~1 с | 2–4 мин | 10–20 с |
| 120 страниц | 20 (лимит) | ~3 с | 5–10 мин | 30–60 с |

Что снижает расходы: отбор релевантных фрагментов вместо отправки всего
документа, детерминированная стадия reduce (экономит вызов на каждый документ),
отсутствие повторов для невосстановимых ошибок, `temperature=0` (детерминизм
делает результат кешируемым). Расход токенов возвращается в ответе, счёт за
облачный API не должен становиться неожиданностью.

Разбор PDF и прогон правил уводятся в отдельный поток (`asyncio.to_thread`):
это чистый CPU на десятки секунд, в event loop он блокировал бы все
параллельные запросы сервиса.

## 11. Тестирование

114 тестов, ни один не обращается к реальной модели: вместо неё управляемый
клиент, отвечающий по сценарию. Тест на живой LLM проверяет не код, а погоду.

Тестовые данные - синтетический PDF, собираемый `scripts/make_sample_pdf.py` на
reportlab: структура документации по 44-ФЗ, НМЦК прописью и цифрами, три этапа
со сроками, семь требований, раздел ответственности, таблица штрафов и
колонтитулы на каждой странице. Реальные файлы с ЕИС в репозиторий положить
нельзя (объём, персональные данные), а тестам нужен предсказуемый вход, на
котором известен правильный ответ.

Покрываются: форматы сумм из документации, границы разделов, разбор таблиц,
восстановление грязного JSON, бюджет размера фрагментов, дедупликация при
слиянии, обнаружение галлюцинации, форма запроса каждого провайдера,
классификация ошибок, устойчивость пайплайна к отказу части фрагментов, коды
ответов API.

## 12. Границы применимости и что дальше

Чего сервис не делает сейчас:

- **не распознаёт сканы** - PDF без текстового слоя отклоняется с советом
  прогнать OCR. Интеграция `ocrmypdf`/Tesseract была бы следующим шагом, но это
  отдельная зависимость весом в сотни мегабайт и минуты обработки на документ;
- **не читает архивы и не ходит на ЕИС** - на вход один PDF, а не ZIP с
  комплектом документации и не ссылка на извещение;
- **не понимает Excel-приложения** - смета и график в `.xlsx` остаются вне
  анализа;
- **не хранит историю** - сервис без состояния, каждый запрос независим.

Отдельно про правовой режим: сервис отдаёт выжимку, а не юридическое
заключение. Ключевые условия перед подачей заявки проверяются по исходному
документу - для этого в ответе есть номера страниц и дословные цитаты. Сам код
распространяется по MIT ([LICENSE](../LICENSE)), лицензии зависимостей и условия
использования моделей сведены в
[THIRD_PARTY_LICENSES.md](../THIRD_PARTY_LICENSES.md).

Направления развития по убыванию отдачи: OCR для сканов, приём ZIP с разбором
комплекта документов (реестр, ТЗ, проект контракта - с указанием источника
каждого факта), кеш по хешу файла (документацию одной закупки проверяют
многократно), сравнение двух версий документации (заказчики публикуют
изменения, и важно видеть, что именно поменялось в цене и сроках), выгрузка
выжимки в XLSX для закупочного отдела.
